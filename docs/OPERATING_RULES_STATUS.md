## Implemented: main-admin Business settings

Open `/business-settings`. Six sections cover booking requirements, installments, collections, late fees, landowner defaults and commissions. Only `super_admin` **and** `business-settings.manage` can read/write; granting the ability to a different role does not bypass the main-admin boundary. Ordinary admin discount approval is a separate future action.

Each section can be saved incomplete. Missing fields remain visible; zero percent/zero grace are explicit values, not treated as missing. Dropdowns start unset; only the requested method/frequency option lists are preselected on a new form, and remain unsaved until submitted. Booking checklist selections must include a signed booking form. An unset threshold or hold-conversion rule cannot supply an implicit booking default. Existing manual hold/block/release authority is unchanged.

Percentages remain decimal strings to four places in JSON. Fixed amounts use the shared positive `DECIMAL(18,2)` input limits and two-place normalization. Invalid combinations (such as a whole-contract percentage triggered on every collection, fixed per-booking commission with a percentage base, or disabled fees with retained fee amounts) fail validation. This screen does not calculate installments, accrue obligations or post receipts.

The [policy action](../app/Domain/Configuration/BusinessPolicies.php) validates whitelisted fields/enums, normalizes exact values, locks fresh actor + installation + section, checks optimistic version and atomically saves append-only before/after history. No-op saves account for MySQL JSON object key ordering. A history failure rolls back the policy. [Definitions](../app/Domain/Configuration/PolicyDefinitions.php) provide shared server-owned labels/options/validation metadata for the [UI](../resources/js/pages/business-settings/index.tsx). [Migration](../database/migrations/2026_11_03_000300_create_business_policies.php) adds restrictive FKs, positive versions and unique policy/version history.

## Implemented: private customer identity and evidence

The [identity migration](../database/migrations/2026_11_03_000400_add_customer_identity_and_documents.php) adds nullable encrypted CNIC/address and append-only document metadata. Existing contacts remain valid. CNIC accepts 13 digits or the standard hyphen format and stores normalized digits through Laravel encryption; address is also encrypted. Both are hidden from ordinary model JSON and exposed only in an already scoped profile. Directory/search/sales props do not expose identity; there is no unapproved global CNIC uniqueness assumption.

Identity-bearing creation payloads use a keyed HMAC, including support for configured previous app keys, to avoid retaining a brute-force-friendly plain identity hash. Old contact-only creation keys retain their existing replay behavior. Audit records store changed field names and assignment/document IDs, never identity/address/contact snapshots or original filenames.

The [document controller](../app/Http/Controllers/CustomerDocumentController.php) accepts only content-validated JPG/PNG/PDF up to 10 MB; photographs must be JPG/PNG images within pixel limits. Files receive server-generated names on a dedicated private disk outside the public root. There is no public URL, original filename or editable storage path. Downloads recheck current customer assignment, bind document ID to customer, require verified session access and send attachment/no-store/nosniff/sandbox headers. Downloads and uploads are audited. Missing files return 404. Upload audit/DB failure rolls back metadata and removes the newly stored file; process crashes between filesystem and database commit still require orphan reconciliation in operations.

There is no destructive replace/delete route: upload new evidence while preserving old metadata. This is not approval/signature verification or an antivirus system. Malware scanning/quarantine, formal retention/legal-hold rules, sensitive-data access policy, storage encryption and restore testing remain live-release gates. An uploaded payment-evidence file is not a posted receipt and cannot independently satisfy the future down-payment gate.

Inertia browser history encryption is enabled, and the sign-in page clears its history encryption key. This prevents an old customer profile being restored through the Back button after logout. Browser tests verify encrypted history state, the sign-in view with no identity data after Back, and an authenticated-route reload returning to sign-in. Inertia can preserve the attempted URL during history recovery; a preserved URL does not mean the protected profile was restored. Production HTTPS is required for the browser's secure-context cryptography; loopback local testing also supports it.
